## 10.1. Результат: **23/30 до исправления → 29/30 после** (цель ≥28/30 — достигнута)

Методика (см. 10.4) одна и та же для обоих прогонов: Playwright + Chromium с эмуляцией iPhone, троттлинг CDP (1.5 Мбит/с, задержка 400 мс, 4× замедление CPU), «до» — реальный живой сайт `https://nfhours.github.io/library/`, «после» — тот же воркфлоу, но локальный сервер, раздающий текущую (неподтверждённую, незакоммиченную) копию этого воркtree на порту 8931. На каждой из 30 ссылок: открыть, дождаться первых меток страниц (признак, что контент отрисовался и первый прыжок уже случился), подождать ещё 5 секунд (имитация дозагрузки картинок/шрифтов на медленной связи), определить, какая страница 1626 года видна у верхней границы экрана, сравнить с страницей, которую цитирует сама ссылка указателя.

Это зафиксировано здесь открыто, а не скрыто за цифрой.

## 10.2. Причина и исправление

**Причина**: функция `snap()` внутри `renderChapter` (app.js) прыгала к цели ровно два раза — сразу и один раз после `document.fonts.ready` — и больше никогда не пересчитывала позицию. На медленной связи гравюры выше цели (`<img loading="lazy">`, они у многих из них ещё и за пределами исходного экрана до прыжка, то есть по-настоящему начинают грузиться только после самого прыжка) успевают дозагрузиться и, хоть у них есть атрибуты `width`/`height`, зарезервированное место — существенно после второго прыжка. Из-за этого итоговая позиция чуть смещается вниз/вверх, и читатель оказывается на соседнем листе оригинала 1626 года, а не на том, что процитирован.

**Исправление** (`app.js`, функция `renderChapter`, блок `if(target){...}`):
- `snap()` теперь перезапускается при каждом `load`/`error` каждой ещё не загруженной (`!img.complete`) картинки внутри тела главы — до тех пор, пока либо все такие картинки не разрешатся, либо читатель сам не начнёт скроллить/трогать экран/нажимать клавиши (тогда скрипт сразу перестаёт мешать, подписки на `wheel`/`touchmove`/`keydown` снимаются после первого срабатывания). Есть страховочный таймаут в 12 секунд, чтобы не держать слушатели вечно, если какая-то картинка вообще не долетит.
- На все `<img>` гравюр (и в `figsHtml`, и в подписи-блоке `cap` внутри `blockHtml`) добавлен инлайновый `style="aspect-ratio:W/H"` — поверх уже существовавших HTML-атрибутов `width`/`height` (у всех 251 гравюры книги они и раньше были заданы, проверено по данным — отсутствующих нет), чтобы раскладка резервировалась максимально надёжно независимо от деталей UA-стиля конкретного браузера.
- Это единственный общий код для всех трёх точек входа из задания: ссылки указателя (`#/<slug>/index`), «Читать в главе» с карточки гравюры/таблички и ссылки из раздела «Имена» — все три построены через одну и ту же функцию `chapterHref()` → маршрут `ch/<slug>/<block>[/<page>]` → один и тот же `renderChapter`/`snap()`. Проверено по коду (не только предположение): `chapterHref` вызывается в деле построения ссылок во всех трёх местах (строки с `ic-nm-ms` для «Имён», `ic-pc-read` для карточки гравюры, `pagesHtml`/`ic-ch-btn` для указателя и карточек статей) — отдельной правки не требовалось, один фикс закрывает все три.

## 10.3. Отдельная находка: реальный баг в данных pagemap (диапазон страниц 95–102 главы diana), не связанный с гонкой скролла

Проверка по вашей наводке подтвердила реальную проблему. В `books/cartari/pagemap.json` для главы `diana` метки страниц 95–99 все указывали на один и тот же «стартовый блок» (60), а 100–104 — на другой («91»), то есть пять подряд печатных страниц визуально сливались в одну метку диапазона, хотя на деле это полнотекстовые страницы с собственным содержанием (не вклейки-гравюры).

Причина — в `tools/build_pagemap.py`/`found_places()`: алгоритм «уточняет» диапазон блоков страницы по номерам блоков из записей указателя (`tavola.json`), которые упоминают эту же печатную страницу. Но для страницы «97» (и нескольких соседних) указатель содержал заведомо ошибочные привязки — например, статья-заголовок всей главы «Диана, Богиня охоты» (которая на самом деле целиком относится к блокам 1–7, то есть к странице 87) оказалась дополнительно привязана к странице 97 с блоком 3. Алгоритм безоговорочно утягивал нижнюю границу диапазона страницы 97 до блока 3, а затем принудительная монотонность (следующая страница не может начинаться раньше предыдущей) «размазывала» эту ошибку на несколько следующих меток подряд, создавая длинные плато.

**Исправление** (`tools/build_pagemap.py`): перед тем как учитывать привязки из указателя, они теперь проверяются на разумность — отбрасываются те, что выходят за пределы ±20 блоков от диапазона, который для этого скана дают сами сверенные главы (`c.page_range(s)`). Пересобран `pagemap.json`; затронуло только 2 главы во всей книге: `diana` (6 строк — 95–104, теперь монотонная последовательность 72→81→91→96→109…) и `plutone` (1 строка — сузилась верхняя граница с 141 до 110, тоже похоже на такую же опечатку указателя). Остальные 23 главы не изменились — проверено диффом JSON построчно.
